SECTION A — THE PROBLEM (Slide: "The Human Cost")
--------------------------------------------------------------------------------
• Mobile-money fraud in Ghana = social engineering + time pressure:
  impersonated SMS, coercive voice calls, OTP read-out, mule transfers.
• Victims are often illiterate or feature-phone users — they cannot read
  English warnings, cannot install security apps, cannot verify sender IDs.
• Existing defenses fail them: network-level blocks cause false positives
  (union leader's 30 calls, 18-year-old's first SIM); consumer apps require
  smartphones and literacy.
• The OTP problem: a genuine MTN OTP cannot be flagged — it IS legitimate
  traffic. The attack is the call around it and the transaction it unlocks.

SPEAKER LINE:
"A subscriber should not need a smartphone, literacy, or a security app to
be protected at the exact moment fraud happens — inside the network."

SECTION B — THE SOLUTION: TWO-MODE FRAUD ENGINE (Slide: Architecture)
--------------------------------------------------------------------------------
CORE PRINCIPLE: "Gemini is an explainer, not a gatekeeper."
Deterministic rules decide in <100ms; LLM/RAG explain AFTER the verdict.

MODE 1 — PREVENTION (real-time, plug-in contract /api/v1/plugin)
• 19 weighted rules across 16 documented interception points
  (sms.deliver, call.connect, payment.authorize, menu.open, sim.swap, …)
• Probabilistic multi-signal scoring — NO single-signal blocking:
  – call.connect: fan-out >25/day (+20), caller SIM ≤24h (+15),
    zero prior contact (+5) — composite only
  – payment.authorize HIGH → delay (10-min cooling) → reject on afterDelay
  – warn/delay only where the contract allows; downgraded elsewhere
• External intel (bounded 1.2s, fail-open): Rancard Glance, SIM-swap check,
  live NIA verify, subscriber profile
• Semantic + lexical RAG over the Fraud Case Corpus grounds every verdict
  in documented Ghanaian typologies (GH01 reversal scam, GH15 phishing…)

MODE 2 — RECOVERY (post-incident forensics — the differentiator)
• FundFlowLedger: every observed directed relationship (SMS, call,
  payment, request, switch, bank leg) recorded cross-subscriber
• GET /fund-flow → live Syndicate Graph: nodes auto-roled
  (suspect/mule/collector/caller), GHS volumes, ledger flags
• GET /evidence-pack/{msisdn} → forensic JSON: incident summary, directed
  fund trail, linked assessments, identity provenance — honest about
  what's verified vs event-supplied claims
• "Generate Evidence Pack" button downloads court-ready JSON for CSA/police

SECTION C — THE DATA MOAT: LOCAL THREAT LEDGER (Slide: "It learns")
--------------------------------------------------------------------------------
• Proprietary sqlite ledger — sub-ms repeat-offender detection
• Writes ONLY on scam-confirmed signals (never bare HIGH scores —
  anti-poisoning by design)
• +25 first confirmation / +45 repeat offender; 30-day expiry;
  influence decays 50% per 14 dormant days — no permanent blacklists
• Exoneration path: DELETE endpoint + shield button in Threat Ledger card
• Survives restarts and external-API outages — demo-proof resilience

--------------------------------------------------------------------------------
SECTION D — INCLUSIVITY: PROTECTION WITHOUT LITERACY (Slide: "For everyone")
--------------------------------------------------------------------------------
OTP READ-OUT DEFENSE (the scenario that breaks other tools):
• Genuine MTN/Telecel/AT OTP → ALWAYS allow. Never flagged. Ever.
• Risky call.connect (warn/reject) → victim marker
• OTP SMS during fresh risky call → bilingual Twi/English advisory SMS:
  "Never read a code to anyone on a call. Hang up now.
   MoMo: MMA obiara nka wo kɔde, fa kyɛrɛ."
• OTP→transaction velocity (+30 corroborating): payment/USSD within
  10 min of OTP → combines with onCallWith (+50) → 10-min delay

WHY IT MATTERS:
• warn = banner on incoming call screen — no reading required
• Twi warnings in 7 UI/playback spots + audio synthesis
• delay = cooling-off period, not accusation — honest transactions pass
• Blast detector capped +30 corroborating — legit bulk SMS (school
  notices) never warns alone (found & fixed via 20-incident load test)

SECTION F — HONEST LIMITS (say these BEFORE judges find them)
--------------------------------------------------------------------------------
• ML model: merged but deliberately NOT wired — untrained model in a live
  decision path is reckless; integration slot built for Phase-2 retrain
  on the 100k labeled sandbox dataset
• Lexical-KB match: corroborating by math (40% match = +20 < warn
  threshold; only ≥80% similarity can warn alone — legitimately suspicious)
• Concurrency: 20 simultaneous incidents ≈ 680ms total on one worker;
  single-process ceiling, Redis-ready for horizontal scale
• Latency: decisions ~10–80ms; external lookups share 1.2s deadline;
  handler timing ≠ end-to-end network latency (say this if asked)
• State: process-local windows + Redis optional; evidence pack covers
  only what THIS deployment observed — honest scope label built in
• Credentials pending: NIA live verify, warning SMS, subscriber profile,
  Glance — all fail-open, activate when SANDBOX_* keys are configured

SECTION G — Q&A BANK (evidence-based answers)
--------------------------------------------------------------------------------
Q: False-positive rate?
A: Quote the Fraud Console scorecard for the current simulator run.
   Local regression fixtures are software checks, not the live scorecard.
   Design goal: corroborating-only signals — nothing warns alone.

Q: Latency?
A: Handler decisions ~10–80ms observed; bounded lookups capped at 1.2s.
   End-to-end network latency measured separately in the Console.

Q: Does NIA verify Ghana Cards?
A: Live verify wired (POST /nia/v1/verify) — activates with credentials;
   until then local format/SIM-count heuristics only, clearly labeled.

Q: Do Gemini/RAG decide blocks?
A: No. Post-decision enrichment only — semaphore-bounded (4 concurrent,
   8s queue) so a 55-incident burst can't 429 or delay verdicts.

Q: OTP fraud / illiterate users?
A: The flagship answer — see Section D. Genuine OTPs untouched; defense
   on the call before and transaction after; Twi advisory + cooling delay.

Q: What happens when fraud succeeds anyway?
A: Recovery Mode — fund-flow graph traces observed hops, evidence pack
   packages identity provenance + fund trail + Glance report refs for
   CSA/police. Most teams only prevent; we also recover.

Q: Can it handle simultaneous events?
A: Verified: 20 concurrent incidents, 680ms total, correct verdicts.
   Atomic per-subscriber windows; Redis backend for multi-worker.

Q: Why not just use Glance?
A: Glance is one input among several — we correlate it with typology
   rules, behavioral velocity, cross-channel precursors, and our own
   ledger. And we feed confirmed frauds BACK to the shared network.
