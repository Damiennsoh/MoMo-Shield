EVIDENCE RULE FOR THIS SCRIPT
Only claim a sandbox interception, a judge score, or end-to-end latency when it
has been observed in the current sandbox session and the result is visible in
its Fraud Console. The local regression scorecard is not the InnoFemme Fraud
Simulator. Do not quote its fixture precision/recall, estimated protected
amount, or local timing as live judge results. The dashboard's event latency is
service-side timing, not end-to-end network latency.

EXECUTIVE OVERVIEW
MoMo Shield is a fraud-assessment plug-in for selected InnoFemme carrier
interception points. It applies deterministic rules to SMS, call, payment,
menu, and SIM-swap event payloads and returns the documented plug-in decision
shape. Optional threat-intelligence lookups are bounded and fail open. The
sandbox bridge and hook registration must be configured separately before
claims of live interception are made.

[0:00 - 0:40] PART 1: THE PROBLEM
Speaker:
"Mobile-money fraud often combines social pressure with a time-sensitive
payment: an impersonated message, a coercive call, and a transfer request. A
subscriber should not have to install a separate smartphone app to receive a
warning at the point where that interaction is being assessed.

MoMo Shield explores an in-network response: assess relevant events before the
configured sandbox step proceeds, then return a concise allow, warn, reject,
or payment-delay decision."

[0:40 - 1:35] PART 2: PLUG-IN DECISION PATH
Speaker:
"The backend accepts the documented InnoFemme plug-in contract at
/api/v1/plugin. The selected points are sms.deliver, call.connect,
payment.authorize, menu.open, and sim.swap. The bridge forwards sandbox calls
to this endpoint; the separate internal /api/v1/webhook/sandbox route is not
the plug-in contract.

For example, the call rule requires all of these supplied signals: a caller
SIM registered within 48 hours, more than 20 numbers called that day, and no
prior calls between the parties. A single high call count is not enough. For
high-risk payments, the response can impose one 10-minute delay; a subsequent
payment marked afterDelay is rejected if it remains high risk."

Speaker:
"The synchronous verdict is based on deterministic rules, event-provided

lookups when configured. Gemini and semantic RAG enrichment run after the
plug-in verdict; they are not represented as live decision inputs. Our
reported handler timing is not a network-to-network latency measurement."

[1:35 - 2:20] PART 3: SIGNAL QUALITY & RESILIENCE
Speaker:
"We made the boundaries explicit. NIA is not queried: Ghana Card format and
SIM-count checks are local heuristics over supplied values. Glance and network
SIM-swap lookups are optional, time-bounded, and fail open when unavailable.
The system does not invent seeded live-risk results.

Within one backend process, subscriber event-history updates are atomic, and
the plug-in can assess overlapping SMS, calls, and payment events. This does
not yet prove multi-worker or distributed-state correctness. We record those
limits rather than claim production-scale capacity from a local test."

--------------------------------------------------------------------------------
JUDGES Q&A — EVIDENCE-BASED ANSWERS
--------------------------------------------------------------------------------

Q: "What is the measured false-positive rate?"
A: "We will quote the value shown by the InnoFemme Fraud Console for the
   current simulator run. The repository's fixed local regression fixtures
   are useful for software checks but are not the live judge scorecard."

Q: "What is the latency?"
A: "The response contains backend handler timing. Optional network lookups
   have a shared configurable timeout budget capped at 1.2 seconds, but we
   have not measured end-to-end p95 latency through the live sandbox here."

Q: "Does NIA verify the Ghana Card?"
A: "No. The current code only checks the supplied card's format and supplied
   SIM/account counts. It does not call or verify against the NIA registry."

Q: "Do Gemini and RAG determine whether an event is blocked?"
A: "No. For the plug-in path, semantic RAG and Gemini intent enrichment are
   deferred until after the synchronous decision so they cannot hold up the
   sandbox response or change that verdict."

Q: "Can it process simultaneous event types?"
A: "The in-process event window is updated atomically and optional lookups are
   bounded. The current state is process-local; multi-worker deployment would
   require shared atomic state and a separate load test."
