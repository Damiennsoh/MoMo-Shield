### Part 1: Inclusivity & Accessibility (The "Built for the People" Strategy)

Your intuition is 100% correct. A visual banner on a screen is useless to a blind person or someone who cannot read. Here is how **MoMo Shield** factors in every user type, and how you explain it to the judges (MTN, NGOs, Donors):

#### 1. The Blind and Illiterate Users (Voice-First Intervention)
*   **The Problem:** They cannot read an SMS or a smartphone push notification.
*   **The Solution:** **Audio/IVR (Interactive Voice Response) Intervention.** 
*   **How it works in your system:** When the engine hits a HIGH risk score (75+), it doesn't just send a text. It triggers an automated voice call (via the Telco's IVR system) to the victim's phone. 
*   **The Pitch to Judges:** *"For our blind and illiterate users, MoMo Shield is voice-first. When we detect a scam, we trigger an automated IVR call in Twi or English: 'Kɔkɔbɔ! Do not share your PIN.' We don't rely on literacy; we rely on audio."* (This is why your pre-recorded Twi audio idea is so critical).

#### 2. Feature Phone Users (USSD & SMS)
*   **The Problem:** They don't have smartphones, so they can't receive app push notifications.
*   **The Solution:** **USSD Push and SMS Alerts.**
*   **How it works:** The Telco's network intercepts the USSD session (e.g., `*170#`) before the PIN is entered. The network pushes a USSD menu to the feature phone: *"WARNING: Suspicious activity. Press 1 to Cancel, Press 2 to Proceed."*
*   **The Pitch to Judges:** *"Our engine is Telco-agnostic. It sits on the server side. Whether the user is on a 2005 Nokia using USSD or an iPhone 15 using the MoMo App, our API intercepts the transaction request at the network level."*

#### 3. Android/Smartphone Users (App & OS Level)
*   **The Solution:** In-app banners, OS-level push notifications, and SMS.

**Summary for the Pitch:** *"MoMo Shield protects the user on the device they already have. We don't ask them to download a new app. We adapt our intervention—Voice for the blind, USSD for feature phones, Push for smartphones."*

### Part 2: Killing the "Hardcoded Play Button" (Dynamic Detection)

You are absolutely right to be worried about the "Play Scenario" button. If a judge sees you click a button and a pre-scripted animation plays, they will think: *"This is just an `if/else` statement. It won't work on real, messy data."*

To prove this is a **Live Decision Engine**, we need to change how the demo is initiated. We move from a **"Scripted Replayer"** to a **"Live Threat Injector."**

Here are three ways to implement this in your Streamlit dashboard, ranging from easiest to most impressive:

#### Method 1: The "Judge-in-the-Loop" Live Text/Mic Input (Easiest & Most Effective)
Instead of a dropdown menu of scenarios, add a **"Live Threat Monitor"** tab to your dashboard. 
*   **The UI:** A simple text box (or a microphone button) that says: *"Type or speak a suspicious message in Twi, English, or Pidgin..."*
*   **The Action:** The judge types: *"Mepa wo kyɛw, send your OTP to unblock your account."* or your ML partner speaks it into the mic.
*   **The Backend:** Your FastAPI engine receives this raw text. The deterministic rules catch "OTP" (+30 pts). The Gemini API analyzes the Twi/English code-switch and catches "Authority + Loss Aversion" (+20 pts). 
*   **The Result:** The dashboard instantly updates: **Risk: 85/100 (HIGH)**. The mock phone shows the intervention.
*   **Why this wins:** It proves your engine is evaluating *unseen, live data* in real-time. It is not hardcoded.

#### Method 2: The "Raw Event Injector" (For Telemetry)
For scenarios that rely on backend data (like GH18 New Device Takeover), don't use a "Play" button. Create a **"Manual Event Ingestion"** form in your Streamlit sidebar.
*   **The UI:** Simple input fields: `MSISDN`, `Event Type (Dropdown)`, `IMEI`, `Amount`.
*   **The Action:** You or the judge manually types in a new IMEI number and clicks "Inject Event."
*   **The Backend:** The engine evaluates this raw event against the state window. It sees a new IMEI (+40 pts) and flags it.
*   **Why this wins:** It shows the judges the actual data your engine consumes, proving it's a real data-processing pipeline, not a video game.

#### Method 3: The "Sandbox Listener" (The Ultimate Proof)
If the InnoFemme hackathon provides a WebSocket or an API endpoint for their sandbox:
*   **The UI:** A status indicator that says: *"Listening to InnoFemme Sandbox Stream... 🟢 Live"*
*   **The Action:** As the sandbox generates random events, your dashboard updates live.
*   **Why this wins:** It is the ultimate proof that your system works on external, unprescribed data.

### 🛠️ How to Update Your Code for the "Live Threat Injector"

To implement **Method 1** (which is the most impressive for the Q&A session), add this to your `app.py` in a new tab:

```python
import streamlit as st
from app.services.api_client import assess_event # Your existing API client

st.title("🛡️ Live Threat Monitor")
st.markdown("Test the engine with unprescribed, live inputs. Type or speak a scam message below.")

# 1. Live Text Input
user_input = st.text_area("Enter a suspicious SMS or Voice Transcript (Twi/English/Pidgin):", height=100)

# 2. The Live Assessment Button
if st.button("🔍 Analyze Live Signal"):
    if user_input:
        with st.spinner("Engine processing..."):
            # Construct a raw communication event dynamically
            live_event = {
                "event_id": "live-test-001",
                "msisdn": "+233240000999", # Dummy number
                "event_type": "communication",
                "channel": "VOICE",
                "text_or_transcript": user_input,
                "timestamp": "2026-11-28T12:00:00"
            }
            
            # Send to your FastAPI backend
            response = assess_event(live_event)
            
            # Display the dynamic result
            if response.risk_tier == "HIGH":
                st.error(f"🚨 HIGH RISK DETECTED! Score: {response.risk_score}/100")
                st.write(f"**Reason:** {response.triggered_rules[0].description}")
                st.info(f"**Twi Warning:** {response.twi_warning_message}")
            else:
                st.success(f"✅ LOW RISK. Score: {response.risk_score}/100. Transaction allowed.")
```
