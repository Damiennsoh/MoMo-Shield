# MoMo Fraud Project Report

**Report date:** 23 November 2026  
**Dataset status:** Synthetic rehearsal dataset  
**Primary mock run:** `100,023` transactions, `22,005` fraud transactions, `21.99994%` fraud

## Executive summary

The project now has a working, reproducible mock-data prototype rather than a
production fraud system. It can generate a large synthetic world, replay
transactions and side-channel events in timestamp order, construct leakage-aware
features, train and calibrate several fraud models, save the resulting pipeline,
score a precomputed feature vector through FastAPI, and produce operational
metrics and notebooks.

The strongest current mock result is the calibrated ensemble. It reached
`0.9945` PR-AUC and caught `51.23%` of test fraud at a measured test
false-positive rate of `0.0%`. The amount-weighted recall was `63.29%`, meaning
it stopped approximately `63.29%` of the synthetic fraud amount in the test
period.

These numbers are not evidence of real-world performance. They come from data
described and generated by the mock sandbox assumptions. They can validate
the implementation and show the intended analysis workflow, but they must not
be treated as an expected result on the real sandbox or mobile-money traffic.

## Mock dataset used

- Source rows: `100,023`

The exact generator command is:

```powershell
python scripts/mock_sandbox.py --people 4000 --tx 78018 --cases 8720 --seed 7 --total-transactions 100023 --fraud-fraction 0.22 --out data/mock_full
```

The rebalance step selects the requested 22% fraud subset and 78% legitimate
subset after the scenario generator runs. This preserves the ten fraud kinds
and fraud-case structure while matching the description in the supplied
scenario specification.

## What has been built

### Data and reproducibility

- A mock sandbox generator for people, Ghana Cards, SIMs, wallets, agents,
  merchants, bank accounts, calls, texts, complaints, and transactions.
- CSV loading and internal-column mapping support.

- Saved processed feature and test-decision tables in `data/processed/`.
- Saved model bundle in `models/fraud_pipeline.joblib`.

### Point-in-time features

The replay process builds features from events strictly earlier than each
transaction. Same-timestamp events are applied after transactions are scored,
which reduces same-time leakage risk.

The feature families include:

- Transaction velocity over 1 hour, 24 hours, and 7 days.
- Payer in/out amounts and historical payer amount profile.
- New payee and unique payee/sender counts.
- Payee fan-in, fan-out, and pass-through ratio.
- Near-limit and amount-to-limit features.
- Calls shortly before a transaction.
- Prize, urgent, credential, and credit-claim text flags.
- Fake-credit ledger mismatch.
- Recent SIM replacement and PIN reset.
- Recent SIM/PIN combinations.
- Payer and payee wallet age.
- Hour, weekend, and night features.
- Transaction-type indicators.
- Isolation Forest anomaly score.

Labels, fraud scenario, fraud role, and fraud case are not used as model
features.

### Modeling

The pipeline currently includes:

- Transparent rule baseline.
- Class-weighted logistic regression.
- LightGBM `LGBMClassifier`.
- Isolation Forest fitted only on legitimate training-period rows.
- Probability averaging for ensemble fusion.
- Isotonic calibration on validation predictions.
- Validation-selected thresholds at a 1% false-positive target.
- Expected-loss decisions using probability multiplied by transaction amount.
- Allow, warn, hold, and freeze actions.
- SHAP explanations for the LightGBM component.
- A fixed-snapshot experimental PyTorch GraphSAGE-style edge classifier.
- TF-IDF and transformer-training utilities for future independent text labels.

2. `02_leakage_audit.ipynb` - timestamp replay, feature/label separation,

### Interpretation

A recall of 51.23% means the ensemble caught about 51% of fraud transactions
in the mock test split. The amount-weighted recall of 63.29% means it caught a
higher percentage of the fraud amount than of fraud-row count, because it found
some of the larger fraud transactions.

PR-AUC is strong, but it should not be the only result. The synthetic prevalence
is 22%, much higher than most real fraud prevalence. The test false-positive
rate is also measured on synthetic legitimate activity and is not proof of real
customer-friction behavior.

The high ranking metrics may include mock-generator artefacts. Future evaluation
must check feature importance, fixed repeated amounts and timings, per-scenario
behavior, and unseen fraud kinds.

**Needed to complete it:**

## Deep text and GraphSAGE in the latency architecture

The transformer and GNN must not be placed on the critical USSD response path
until their latency and availability are proved.

Recommended architecture:

```text
USSD/payment event
  -> timestamped state update
  -> rolling tabular/graph aggregate features
  -> LightGBM/anomaly/calibration score
  -> allow/warn/hold/freeze decision
  -> immediate or near-immediate response
  -> queued deep text/graph analysis
  -> later analyst case update and dashboard
```

The Transformer can extract manipulation intent, urgency, authority
impersonation, prize language, and novel scripts. The GNN can add payment-network
relationships, but both belong in a deep/asynchronous lane unless benchmarked
for the real SLA.

If a deep service times out, the system should use the fast tabular decision,
mark deep features unavailable, and continue. It should not block a USSD session
indefinitely.

## What prevents the fraud detection from working well

The main weak points are not the coding implementation alone:

1. No real labeled sandbox data in this workspace.
2. No independent text labels.
3. No real live event contract or state store.
4. No independently reviewed Twi warnings.
5. No real fraud prevalence or customer-friction costs.
6. No real decision permissions or recovery workflow.
7. No offline/live parity evidence on real event timing.
8. No complete end-to-end latency test.
9. Synthetic data may leave repeated timing and amount artefacts.
10. Missing external-network or cross-provider visibility may hide mule chains.

To improve performance, the project needs real labels and real cross-table
relations before any stronger model claims. Feature quality, point-in-time
correctness, and operational thresholds matter more than adding another neural
network.

Before tuning:

1. Define validation and blind time boundaries.
2. Assign cases as groups.
3. Exclude crossing cases.
4. Fit preprocessing on training only.
5. Calibrate on validation only.
6. Tune thresholds on validation only.

### Priority 3: live feature parity

Implement and test:

- One replay feature function for training and serving.
- Event-by-event state update.
- Transaction timestamp and equal-time handling.
- Graph and call/text/SIM state windows.
- Automated offline/live output comparison.

### Priority 4: cost-aware thresholds

Replace placeholder costs with approved values:

- Warn cost.
- Hold cost.
- Freeze cost.
- Customer recovery cost.
- Potential prevented-fraud amount.
- Acceptable false-positive count or false-positive rate.

Actions should be limited to those the real sandbox supports.

### Priority 5: deep text asynchronously

After independent text labels exist:

1. Train TF-IDF baseline.
2. Fine-tune the multilingual transformer.
3. Compare against keyword and ledger-mismatch features.
4. Calibrate text probabilities.
5. Enqueue as async case enrichment.
6. Do not block the immediate USSD decision.

### Priority 6: static graph to rolling graph

Keep GraphSAGE optional until:

- Live graph state exists.
- Offline/live graph replay matches.
- Rolling graph model improves a fixed validation baseline.
- Memory and update latency are acceptable.

### Priority 7: Twi governance

Add reviewed English/Twi templates and approval metadata. The API should
continue to block missing or unapproved translations.

### Priority 8: complete SLA test

Measure the complete p95 request:

```text
event ingest + state update + feature build + model score +
calibration + policy decision + HTTP response
```

Reserve response-budget margin below three seconds. A hard internal deadline,
for example two seconds, leaves time for network variability and avoids
depending on an aspirational p95 result.

## Model limitations and honest conclusion

The current project proves that the engineering and evaluation pattern is
plausible. It is not yet proof that the prototype detects real fraud, is
unbiased across Ghanaian demographics or fraud kinds, meets a telecom SLA, or
integrates safely with the live sandbox.

The strongest next step is a real-data, leakage-controlled baseline:
rules, logistic regression, LightGBM, anomaly detection, and existing historical
call/SIM/text features. Transformer and GNN components should remain secondary
until independent labels and live-state parity exist.
